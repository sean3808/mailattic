## Context

信庫只存純文字內文。`#14` 原本的提案是保留原信 HTML，免得表格攤平後欄位錯位。追問之後，Sean 真正擔心的不是外觀，而是 AI 讀客戶的報價或訂單表格時，把某個值看成另一欄的值。

2026-11-05 實測（數字都是本機抽樣，不是全量）：

- **IMAP 路徑**（本專案的 HTML 轉換器）：`#14` 第 5 點讓空白格保留位置之後，最近 7 天的 554 封裡有 182 封含表格。其中真正會配錯欄的有 13 封，全是合併儲存格；另有約 20 封是「一列只剩一格有值」或「格內換行」，屬於退回舊輸出的形狀。
- **信同時帶純文字版時，存的是寄件端的純文字版**：入庫時只要有非空的 text/plain，就只用它，HTML 整份丟棄；IMAP 和 PST（readpst 解包）兩條路徑都是如此。本機抽樣的 182 封表格信中有 163 封屬於這種情況，所以上一點的轉換器改進只作用在約一成的表格信。寄件端用 Outlook 產生的純文字版，表格的格子只要包了 `<p>` 或 `<div>`，一列就會被拆成一格一行，空白格消失；真實信件多半是這種格子（用未存檔的 MailItem 合成測試可重現）。抽 3 個 PST、約 260 封含表格的信，只有約 3% 的表格列在 Outlook 的文字裡有完整對應的一行（比對器偏嚴、抽樣非隨機，只能當指標）。信庫裡的文字已經無法還原欄位對應。
- 本決策初稿曾把 PST 信的內文來源誤記為 Outlook `MailItem.Body`；實際上是 readpst 解包後交給本專案的 parser（2026-11-05 查證後更正）。

## Decision

不在信庫存原信 HTML。[[Table fidelity]] 的標準定為「要嘛轉對，要嘛明講可能失真」，由三層來守：

1. **轉換器轉對**：能確定欄位對應的表格，照位置輸出，空白格、合併儲存格都要留位。信同時帶純文字版與 HTML 時，HTML 只要含資料表格，就改用 HTML 轉出的文字；不含資料表格的信照舊用純文字版。
2. **轉不對就標 [[table fidelity warning]]**：判斷不出欄位對應的表格，在內文標一行提示，不讓它看起來像正常文字。
3. **需要時 [[original export]]**：讀到提示的人從原始來源（PST 或郵件伺服器）把那封信取出成檔案，用 Outlook 打開核對；另開票，排在 `#14` 之後。

PST 匯入的舊信回 PST 重新解包（與當初匯入同一條 readpst 路徑，依原位置配對並以 Message-ID 驗證），交給本專案的轉換器重做內文：先在複本資料庫上試跑、量時間和影響，再由 Sean 對正式信庫執行。先前從 IMAP 進來、伺服器上已經刪掉、也不在任何 PST 裡的信，接受維持現狀；試跑時把封數算出來，寫進 AI 讀信說明。

## Rejected alternatives

- **保留原信 HTML 並用於引用**（`#14` 原提案的 B／C）：要加 schema、在引用前清除外部內容（多出一塊新的安全面），還要整批回補。剩下的外觀問題只影響經 bes 寄出的引用，不值得這個成本。
- **只寫一句整批警告「PST 舊信的表格可能攤平」**：成本最低，但 AI 分不出是哪幾封；九成的信在這一批，而查歷史報價正是最容易看錯的場景。
- **要求每種表格形狀都轉對**：合併儲存格這類形狀，轉成一行文字本來就無法沒有歧義；要做到全對，只能存 HTML。
- **只替被標提示的信另存原始表格**：可以讓 AI 自己讀表格結構，但等於少量存 HTML；先用匯出原信，覺得常被打斷再回頭考慮。

## Consequences

- 「轉錯了又沒提示」是唯一會讓 AI 看錯欄位的路徑，要用測試盯住。
- PST 舊信重做內文是一次正式信庫的大量改寫，照常規由 Sean 親跑。
- `#14` 第 1–4 點（存 HTML、清理外部內容、字體、回補）由本決策取代；字體已由 `#13` 完成。
