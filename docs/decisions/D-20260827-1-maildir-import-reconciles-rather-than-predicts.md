## 背景

`bes import --maildir` 是 `#154` 補的 CLI 入口。匯入本身不難——既有的 `import_maildir_sources` 每天在跑，走過大量郵件。難的是**匯不到的時候要看得出來**。

maildir 的讀取只走 `<folder>/{cur,new,tmp}/**`。放在其他位置的信件檔會被跳過，而跳過是無聲的：沒有資料列、沒有 `ingest_failures`、`failure_count` 為 0、exit 0。對一個用途是回答「我們來往過什麼」的檔案庫，這是最不能接受的失敗形狀——查詢會給出「沒有這封信」，而那個答案與「真的沒談過」無法區分。

第一版守門的做法是**事先猜哪些檔會被讀到**：掃一次目錄，看有沒有 bucket。跨模型審查隨後在五種不同的目錄擺法上各找到一個洞：

1. 整個目錄都是散裝 `.eml`
2. 好資料夾旁邊有壞資料夾（守門用整棵樹 `any()`，一個過就全過）
3. 同一資料夾內、bucket 旁邊的散裝檔
4. 點開頭的資料夾（`resolve_maildir_sources` 從不把它們當 folder）
5. 名為 `cur` 的普通檔案（`exists()` 放行，`rglob` 對它回空）

前三個各補了一次補丁。第三次時症狀重複已構成路線錯誤的訊號（同一症狀、不同位置），不是執行不夠好。

## 決策

**不預測，改量測。** 而且量測的基準不是另寫一套規則，是讀信那段程式自己。

`parser.py` 匯出 `iter_maildir_message_paths(source_path)`，作為「哪些檔會被讀到」的**唯一答案**；`MaildirParser.iter_extraction_results` 自己呼叫它。CLI 的對帳是：

> 掃過操作者指定目錄下的所有非點開頭檔案，減去該函式回報的可讀集合。差集就是會消失的信。

差集非空就點名列出並**在建立資料庫之前**以非零結束——不留部分匯入的中間狀態。

另有一道**獨立的形狀檢查**問不同的問題：source folder 底下連一個 bucket 都沒有就報錯。它沒有資料遺失可言（檔案根本不存在），買到的是可辨識性——在此之前「你指錯目錄」與「這個存檔是空的」輸出都是 `Imported 0 messages` + exit 0。

**點開頭的檔案不算信**（`.uidvalidity` / `.mbsyncstate` / 本專案的 `.imap_watermarks.json` 是 maildir 記帳檔），但**點開頭的資料夾內容仍算信**——那裡的檔案讀不到，會被列出。這條規則拿本機 `.mailattic-work/maildir/` 的實際內容對過，否則每一棵真實的 mbsync 樹都會被誤擋。

## 為什麼是這條路

**兩份實作之間永遠有縫。** 守門若自己描述一次版面，它與真正在讀檔的那段就是同一件知識的兩份陳述；只要有一點出入，出入就是一個洞，而每個洞的症狀都一樣（信消失、系統說成功）。補粒度是在追縫，第四種擺法遲早會出現。

共用同一份走訪之後，出入在結構上不可能存在——因為只剩一份。上面五種擺法由這一條規則一次涵蓋，未來任何新擺法也是。

代價要講明：多一次目錄走訪（帳號根的規模是幾個資料夾、每個資料夾可能數萬封），而且形狀檢查是**事前擋**、對帳是**事前算**，兩者都在寫入之前。

## 翻案條件

- **讀取規則不再只是「bucket 底下的檔案」時**（例如支援 mbox / emlx 原生解析，或 maildir++ 的點開頭資料夾改為納入），`iter_maildir_message_paths` 要跟著改，對帳自動跟上——但「非點開頭檔案 = 信」這條啟發式要重新檢視。
- **對帳的走訪成本在超大資料夾上成為問題時**：`parser.py` 目前會先 `sorted(rglob("*"))` materialise 整個清單才開始 yield，對帳又走一次。兩者都可改成串流，屬另一張票。

## 不做

- **不退回逐案守門**。五種擺法各補一條的路線已被兩次拍板推翻，記在這裡免得下一輪重新提案。
- **不改 `import_maildir_sources` / `resolve_maildir_sources` 的既有語意**——每日 IMAP sync 走同一條路徑。本次只把走訪抽成函式，行為不變。
