- **相關**：issue `#177`；被取代的敘述在凍結唯讀的 `openspec/specs/cowork-mcp-bridge/spec.md`

## 背景

CoWork 透過 MCP 找一封含兩個特定數字的舊信，四次工具呼叫沒解決，最後是把回傳落地成檔案、用外部 `grep` 找到的。回報書把成因歸給「`keyword` 參數被靜默忽略」。

實測不成立：那些「看起來無關」的信，body 都真的含關鍵字，只是全在**引用歷史**裡，而 `snippet` 取的是內文開頭。真正的成因是排序 —— `search_messages` 無論有沒有 keyword 都 `ORDER BY sent_at DESC`，於是 `--limit 20` 是按「最新」切候選集，而**原始報價依定義是最舊的那一封**：之後每一封回覆都在引用它，每一封都含同樣的詞，也都比它新。

## 決策

有 `keyword` 條件時，`search_messages` 改用 `ORDER BY bm25(message_fts)`，時間序降為 tiebreaker。**沒有 keyword 時維持原本的時間新到舊**，一個字都不改。

同時每筆結果帶兩個純量說明命中理由：`match_field`（`body` / `subject` / `null`）與 `match_in`（`new` / `quoted` / `null`），`snippet` 在有命中時改以命中處為中心。

`match_in` 講的是**snippet 顯示的那個命中**在哪一區，不是「所有查詢詞分別出現在哪些區」。後者在跨模型 review 時被指出會誤標：原始信本身通常也在回覆前一封來信，而那封來信會提到相同的詞 —— 新內容有完整查詢、引用區有一個零星詞，per-region roll-up 會說「兩邊都有」，而 skill 正是教呼叫端篩「證據是自己寫的」那一封。綁定到實際顯示的命中同時也保證兩者一致：不會發生「標 `new` 但 snippet 取自引用區」。

字面定位採**整 token** 比對（與 `unicode61` 索引一致），不是純子字串：否則查 `art` 會在 `partial` 裡命中，把一封其實靠收件人命中的信報成 `match_field: body`，並把 snippet 指向使用者沒問過的詞。CJK 詞不套用邊界檢查 —— 索引是 unigram 切分，子字串命中就是索引的語意。

## 為什麼是 bm25

bm25 的長度正規化正好對上這個問題的形狀：原始那封短、只講價格，後續回覆長、把原文整段引進來再加新內容。同樣的詞數下，短文件得分higher。這不是為了「一般而言比較準」而選它，是因為它對「原文 vs 引用它的長串」這個具體分布給出正確答案。

欄位權重維持 FTS5 預設（subject / body / 收件人 / 附件名等權）。沒有量測支持任何一組自訂權重，先不調。

## 被取代的敘述

`openspec/specs/cowork-mcp-bridge/spec.md` 寫過 `mail_search`「SHALL return ... ordered newest-first」，並有一條同名 scenario。那份 spec 於 2026-08-20 隨 Spectra 鏈退場凍結為唯讀歷史參考（[D-20260820-3](D-20260820-3-migrate-to-contract-anchored-flowback.md)），CLAUDE.md 明定「與現況衝突時以契約段與 code 為準」，且此行為不在五條行為契約內 —— 所以本次反轉不需要走契約變更程序。

但它確實是**當初寫下來的行為**，不是意外，因此值得一份 ADR 而不是靜默改掉。原 spec 檔照凍結規則不修改。

## 代價

- **「找最新的信」變難一點**：給了 keyword 就拿不到時間序。緩解是不給 keyword、或拿到結果後自己按 `sent_at` 重排。判斷是這個代價遠小於「最舊的那封永遠找不到」—— 後者是靜默失敗，前者呼叫端看得見。
- **既有呼叫端的隱含假設會失效**：`bes search --keyword` 的輸出順序變了，skill 與 CoWork 的提示詞若假設過「第一筆是最新」就會錯。已在同一個 change 內更新 `skills/mailattic/`。
- **`match_in` 的準確度受限於引用切分器**：`strip_quote_tail` 找不到邊界時保守回傳全文，該封就報 `new`。這是「沒偵測到引用歷史」的誠實表述，不是保證。
- **帶 keyword 時可用的 `limit` 上限縮小約 8%**：snippet 從 160 放寬到 300 讓每列多約 97 字元。正式庫實測，`limit` 的可交付上限從 60 降到 55（查 `the` 是 45→40）。**`limit=100` 在本次改動之前就已經超預算**，所以這不是把原本能用的呼叫弄壞，但確實有一段區間（如 `limit=60`）從可交付變成拒絕。取捨是接受的：拒絕是大聲的、且錯誤訊息會指名要調哪個參數，而 snippet 正是這次改動的價值所在。`tests/test_mcp_search_attachment_budget.py` 的 ratio 測試把這個成長釘在無 keyword 路徑的 1.15 倍以內。
- **字面定位不折疊變音符號**：索引的 `unicode61` 會把 `cafe` 與 `café` 視為同一 token，字面掃描不會。該方向失敗是安全的 —— 那一列仍然命中，只是回 `match_field: null`（其語意本來就是「命中不在你看得到的文字裡」）。要補齊得兩側都折疊、再把 offset 映射回長度會變的正規化前，對一個中英商務信語料不划算。
- **snippet 落點只看每個詞的前 50 個出現位置**：那是安放窗口的啟發式上界，不影響是否命中。若某詞第 51 次才與另一詞共現，會退回較早、共現較少的窗口。

## 被否決的選項

- **加一個 `sort` 參數讓呼叫端選** —— 目前沒有第二個真實需求支撐它，而多一個參數就多一個呼叫端要猜的旗標。真的出現需要時再加。
- **維持時間序、改用更大的 `limit` 讓舊信也進來** —— 那把問題丟給呼叫端猜參數，而且直接撞遞送預算（見 `#178`）。
- **混合排序（相關性 × 時間衰減）** —— 沒有量測支持任何一組權重，等於用一個猜的公式取代另一個。
