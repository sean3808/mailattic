## Context

[D-20261105-1](D-20261105-1-table-fidelity-without-storing-html.md) 否決了「保留原信 HTML 並用於引用」，理由是剩下的只是外觀問題、只影響經 bes 寄出的引用，不值得加 schema、清理外部內容、整批回補的成本。

2026-11-18 Sean 看了三封實際經 bes 寄出的回信：引用區塊裡客戶的簽名圖變成 `[https://...]` 字樣、表格變成 `a | b | c |`、中文信一兩個字就換行。他指出的風險不只是醜：客戶日後往下翻往來紀錄，會看到自己寄出的信長得不像當初寄的樣子，可能懷疑「以前的信是不是被刪改了」。這是業務信任的風險，是 D-20261105-1 權衡時沒有的理由。

根因（`#136` 診斷）：引用區塊只拿信庫的 `body_text`。信同時帶純文字版時，入庫存的是寄件端的純文字版（D-20261105-1 實測段落），HTML 從頭到尾沒有進到回信。

## Decision

回信的 HTML 引用**原信本身的 HTML**，原信在擬稿當下取回，不存進信庫：

1. 用寄件設定裡的 IMAP 帳號（與寄出後 APPEND 到寄件備份同一個帳號與連線方式），以匯出原信同一套查找與 Message-ID 驗證取回原信 RFC822。唯讀 SELECT、`BODY.PEEK[]`，不改信件旗標。
2. 取原信 HTML 本文（解碼沿用入庫的字元集救援），只去掉主動內容：script、frame、embed／object、表單與其控制項、`<meta>`（含 refresh 轉址）、`<base>`、`<link>`、`on*` 事件屬性、任何屬性值裡的 `javascript:`／`vbscript:` 網址、連結開 `data:` 文件、style 屬性與 `<style>` 內文的 `expression(`／script URL／`@import`（CSS 先照渲染器的讀法去掉註解、解開跳脫字元再判斷，`@\69mport` 一樣算 `@import`）。樣式、遠端圖片、連結、Outlook 條件註解照原樣保留。`<head>` 的 `<style>` 與條件註解依原順序跟著引用走。`<body>` 換成 `<div>` 時保留它的呈現：清理後留在 `<body>` 上的屬性（`id`、`class`、`lang`、`style`……）全部照搬，原信樣式表裡指向它的規則照樣生效；只有 body 專屬的呈現屬性改寫：`bgcolor`／`text`／`background` 轉成對應的 CSS，`link`／`vlink`／`alink` 轉成只作用在引用區塊的連結顏色規則，不是單純顏色值的就不帶。以元素名稱指向 `body` 的樣式規則（`body{…}`）對不到這個 `<div>`，接受此限制。
   - **渲染視圖與遞迴清理**：清理器、屬性／`<style>` `cid:` 收集器、以及後置檢查共用同一份「渲染視圖」定義：live markup，加上每個 downlevel-hidden 條件註解（`<!--[if …]>…<![endif]-->`）內文遞迴當成子文件處理後包回原定界符，加上 downlevel-revealed `<![if …]>…<![endif]>` 區段與混合式條件註解（`<!--[if …]><!-->…<!--<![endif]-->` 及 `<!-- -->` 變體，視為配對的 revealed-section 標記，標記本身原樣保留）。普通註解（非 `[if` 開頭）不屬於渲染視圖，不清理也不收 `cid:`。條件註解內文若無主動內容則原樣保留不重新序列化，避免改寫 Word 的 VML 細節。
   - **Fail-closed 後置檢查**：寫入草稿的最終 HTML 字串會重新 parse、建立渲染視圖並斷言：(a) 無任何主動內容，(b) 渲染視圖中每個必填 `cid:` 都對到草稿實際附上的 image part（`<a href>`／`<area href>` 裡的 `cid:` 屬連結而非圖片，不強制解析，原信有附該 part 時照樣附上、沒有時保留原連結；其餘 `src`／`background`／VML／`style`／`<style>` 的 `cid:` 仍須全部解析）；任何違規或無法分類的結構（未閉合或巢狀條件註解、未知 `<!` 宣告）整段退回信庫純文字並給出原因。
3. 被引用的 `cid:` 內嵌圖以 `multipart/related` 跟 HTML 放在一起，不進附件清單。
4. 寄件設定的字體只套在回信本文與引用標頭，不套在原信上。
5. 取不到或退回時（PST 來源、寄件設定沒有 IMAP 帳號、伺服器上已刪、連線失敗、原信沒有 HTML、原信引用的 `cid:` 圖片在原信裡找不到、後置檢查拒絕）退回信庫純文字，並**一定說明原因與意義**：CLI 印 `Quote: stored text (<原因>)` 與 `Quote notice: <說明>`，MCP 回 `quote_source`／`quote_note`／`quote_notice`。
6. 純文字替代版照舊引用信庫文字。

驗收以客戶原信 `.eml` 為準：引用區塊的可見文字、圖片順序、表格格子、段落數與原信 HTML 本文一致，每個 `cid:` 都在草稿裡找得到。

## Rejected alternatives

- **入庫時另存 HTML**（D-20261105-1 否決的原提案）：要加 schema 並整批回補，而回信幾乎都是回近期的信，原信還在伺服器上；即時取回就夠。
- **只改善純文字的 HTML 排版**（段落、表格轉回 `<table>`）：寄件端純文字版已經丟掉圖片與欄位對應，做不出「跟客戶寄出的一樣」。
- **取不到原信就拒絕擬稿**：PST 時代的舊信與已從伺服器刪除的信會完全無法回覆；改成退回並明講原因，由呈審時的人決定。

## Consequences

- 擬回覆多一次 IMAP 往返（30 秒逾時）；伺服器不通時草稿照樣產生，只是退回純文字並標明。
- PST 來源的錨點仍引用純文字；若之後常回覆 PST 時代的信，再考慮經 Outlook 取 `HTMLBody`。
- 引用的原信 HTML 是外部內容，進入寄出的信。清理範圍刻意只到主動內容，維持「跟客戶寄出的一樣」；若日後出現需要擋的形狀，加在 `reply_quote.py` 的清理清單。
- D-20261105-1 其餘決定（信庫不存 HTML、表格保真三層）不變。
