> **2026-10-03 註記**：`/session-merge-queue` 與它的 gate 3 已退役（`#207`）。本決定對設計文件型變更的處置原則不變，執行者改為當時負責語意審查的流程（`/closeout` 的 semantic-review 格）。

## Context

`/session-merge-queue` gate 3 的既有處置有三條：併進本 PR 修、轉 follow-up 票放行、判定不是缺陷。第二條之所以能成立，靠的是一個沒被寫下來的前提：**會動的東西會出聲**。程式有缺陷，測試會紅、跑起來會噴錯、下游會抱怨，那張票遲早被逼著處理——票只是把處理時間往後挪，不是把它丟掉。

2026-08-12，#117 讓這個前提第一次不成立。那張 PR 的交付物是 `openspec/changes/normalize-packed-recipients/` 的 proposal / design / tasks / delta specs，**沒有任何實作**，tasks 28 項全部未勾，最後一項明文寫著停在正式資料庫寫入之前等另一道授權。第 4 輪停在兩條 Track A Important：

- `design.md:66` 把 Message-ID 定義成不分大小寫比對，而正式資料庫的 unique index 與持久化查詢都是精確比對。
- `source_supplied_rerun`（語意是「先別動，去補來源重跑」）被列為合法人工決策，但 apply 的前置條件只要求「每個 exclusion 都有 completed decision」，於是操作員喊停之後流程照樣寫進正式資料庫。

兩條都不是「以後會被測試抓到」的東西。它們是**指示**：幾週後另一個人（或 agent）打開 `design.md` 照著做，讀的是文件，不是票。而第一條那個落差的後果是把 A 信的收件人清單寫進 B 信，事後的 read-back 比對的是計畫、計畫本身就錯了——不會報錯。

嚴重度分級在這裡也幫不上忙。兩條都被判為 Important 而非 Critical，照既有規則（總輪數達 3 之後，非 Critical 可由人裁定轉 follow-up）是可以放行的。**「Important」量的是缺陷本身有多嚴重，不是它會不會被發現**，而後者才是 follow-up 這個機制的承重點。

`#117` 這兩條各自只是幾句話加一條驗收項目，修的成本以分鐘計；但成本低不是本決定的理由——低成本只是讓這次不痛，規則要處理的是下一次成本不低的時候。

## Decision

**處置對每一條 finding 分別判定。** finding 指向一份「之後會被照著實作」的指示，而且該指示若寫錯，同一份 diff 內沒有執行性 guard 會因此發出訊號時，gate 3 的三條處置只剩兩條：併進本 PR 修，或判定不是缺陷。轉 follow-up 票放行不適用。

主要實例是 Spectra propose 階段的 PR（新增 `openspec/changes/<name>/` 但尚未含實作）。判準不是目錄位置，而是逐條問：**這條 finding 指向的指示若寫錯，同一份 diff 內有沒有執行性 guard 會因為這條錯而發出訊號？** 混合型 PR 裡其他程式碼的測試不構成答案；只有確實涵蓋這條 finding 的 guard 才算。否則只要在同一份 diff 混入任一段有測試的程式碼，就能讓未受保護的設計缺陷轉成 follow-up，重建本決定要封掉的繞道。

**ADR 與 harness-skill 類 PR 不適用本決定。** 它們是 merge 後立即生效的 harness 政策，不是延後到 apply 階段才照著實作的計畫；`#117` 證明的是後者的 follow-up 失效，沒有提供把處置擴到前者的證據。這個排除是 `#144` 明列的不做範圍；把它們納入會讓規則滑成「所有純文件 PR 都沒有 follow-up」，也就是下一節否決的第一個選項。`tests/test_agent_pr_contract.py` 只守 PR 交付契約的唯一正文與 pointer 形狀，沒有涵蓋本決定的 worktree 或 follow-up 語意，因此不構成本排除的理由。

**唯一例外**：該缺陷要定案，需要這張 PR **明文寫在 scope 外**的證據。例外的舉證責任在提出的人，而且要指得出 PR 裡那句排除範圍的原文；「查起來很麻煩」「要跑很久」都不是。

例外用過一次的實例：`#117` 第 1 條的「來源側到底有沒有只差大小寫的 Message-ID」確實要先跑 `collect-pst` 才知道，而該 PR 明文排除抽取。但它**不影響結論**——規劃器的識別語意本來就該與資料庫一致，不論碰撞今天存不存在——所以那一條仍然照本決定併進 PR 修。**例外能豁免的是「查清楚事實」，不是「照著錯的寫下去」。**

## Rejected alternatives

- **一律不給 follow-up（含程式碼、ADR 與 harness-skill PR）**：會拆掉一個運作正常的機制，也把本決定的證據外推到未被 `#117` 證偽的交付物。立即生效的政策與延後 apply 的計畫需要各自的處置證據，不能只因兩者都是文字就綁在一起。
- **維持現狀，交給嚴重度判斷**：這是被 `#117` 證偽的那條。嚴重度量的是後果多大，本決定要處理的是**發現機率**——兩條軸不同，用前者代替後者，正好會在「後果大但不會被發現」那一格失手，而那是最壞的一格。
- **允許 follow-up，但要求在計畫書內留 TODO 標記**：標記住在**同一份會被照做的文件裡**，而實作者讀的是段落不是標記；更根本的問題是它製造第二份正典——文件說一套、票說另一套，兩份都得維護。若標記真的可靠到讓人不照做，那它其實就是「併進本 PR 修」的低配版本。
- **只約束 Spectra propose PR，不寫成逐條 finding 的通則**：規則寫 pattern 不寫 intent，會被「我這份不在 `openspec/changes/` 底下」偷渡（全域 `lessons-learned.md` 已有這條教訓）。所以判準問的是該 finding 指向的未實作指示有沒有自己的 guard，目錄只當實例。

## Consequences

- **設計文件 PR 的輪數會變多**，而它本來就是最容易多輪的類型（`#117` 已經四輪）。這是刻意付的成本：多一輪 review 的代價是可算的，讓實作者照著錯的規格做的代價不可算。
- **`#117` 依本決定處置**：兩條 Important 都併入該 PR 修，不轉票。
- **例外條款會被試著擴大解釋。** 收斂的手段是舉證責任——提例外的人要指出 PR 裡排除範圍的原文。找不到那句話就沒有例外。
- **本決定與 #142 互補但獨立。** #142 處理的是「計畫書型 PR 該用哪一種 review」（計畫審查 vs 程式碼審查），本決定處理的是「審出來的缺陷可以怎麼處置」。#142 落地與否，本決定都成立。
- **反轉成本低，但它擋的失敗是安靜的。** 這是一條 harness 政策，改掉只要改這份文件與 `/session-merge-queue` 的處置段；真正的成本在於：一旦放寬，下一次「照著錯的規格實作」發生時，沒有任何機制會把它連回這個決定。要反轉，先找一個「設計文件缺陷被 follow-up 票確實接住」的實例，而不是找一個「這次修起來很麻煩」的實例。
