## Context

`#175` 的 apply 腳本要對正式庫做不可逆寫入，因此在 `--confirm` 之前有一道授權門。跨模型語意審查（Codex）連續三輪都在這道門上出 findings，每修一輪就被挖深一層：

1. 完全沒有驗輸入。
2. 驗了，但只確認「stage 旁邊有一份 `complete=true` 的抽取摘要」——摘要是獨立檔案，不會因為旁邊的 stage 被換掉而改變。
3. 綁定了 dry-run 報告，但仍是彙總層級：沒綁 canonical 身分、沒綁實際置換 mapping。審查明列的情境是「操作者傳入一顆彙總數字剛好相同的另一顆 canonical DB」。

觸及審查輪次上限後停下做路線檢討（獨立票面驗收走查 + 三方會談，紀錄在 `#175` 的路線變更留言）。走查的關鍵發現：**issue 對這件事的全部要求只有「執行前另外確認一次」一句**，沒寫由誰確認、確認什麼、用什麼機制——整套綁定是實作對那句話的詮釋，不是票面規格。換言之，第二、三輪爭的東西票面本身裁決不了，需要一條原則來定界，否則「發現一個漏的就補一個鍵」沒有終點。

三方會談三席一致認為繼續加欄位是錯的路線；封緘那席另外指出，真正的漏洞不在綁定的嚴密度，而在**沒有任何機制記錄「有人讀過並同意」**，以及 `--canonical` 指到位元組相同的備份副本會全數通過。

## Decision

採用下列判準界定本專案守門的防護範圍：

> **這道檢查要防的狀態，是不是需要「這道檢查的受益人自己刻意去達成」？是 → 不防；否 → 防。**

依此劃出的兩側：

- **防（in scope）**：指錯檔案路徑、用到過期或被截斷的輸入、審核與執行之間的狀態漂移。這一族統稱 **confused deputy**——執行者沒有惡意，只是拿到了錯的東西。本專案的執行者可能是 AI agent，而 agent 正是典型的 confused deputy：它會從過期筆記抄路徑、會用預設值、會把備份檔當正式檔。
- **不防（out of scope，接受為殘留風險）**：操作者刻意構造出與已審核計畫碰撞的輸入。當操作者＝擁有者＝審核者＝唯一受害者時，攻擊者與被保護者是同一個人；一個只能被 principal 自己故意繞過的檢查保護不到任何人——同一個人可以直接刪掉腳本或開 `sqlite3` 手改。

**身分的兩種角色要分開**：身分作為「防偽造」out of scope；身分作為「你指到的是不是你以為的那個檔」in scope。後者不需要任何人違背意圖，只需要打錯路徑，因此 `_BINDING_KEYS` 明確保留 `canonical` 路徑一鍵。

這條判準與本 repo 既有的[行為契約 #2](../../CLAUDE.md#行為契約)（對外寄信的授權 gate 要求 interactive TTY、不存在非互動 bypass flag）一致，也與全域教訓「`--confirm <token>` 是 security theater」同源：那條講的是**認證**（caller 可 hardcode 繞過），TTY 講的是**存在性**（要求一個 agent 物理上沒有的通道）。判準把兩者的差別講成可機械回答的一句話。

> **2026-09-14 補記**：上段括號描述的是當時的契約 #2。`#195`（[D-20260914-1](D-20260914-1-send-authorization-is-conversational-with-draft-fingerprint.md)）已把它改為「與當下草稿相符的指紋，或真 TTY 明文授權，擇一」。判準本身不受影響：指紋防的是「呈審後草稿被換掉」這類 confused deputy，不防 principal 自己不問就寄。

## Consequences

- 這條判準**可反證**，不是憑感覺：對任一個提議的檢查，問「要讓它失效，需不需要 principal 違背自己的意圖？」答案是機械的，不需要開會。
- 停止了「補鍵」的無窮迴圈：`#175` 的綁定收斂為單一 plan digest + digest 依定義看不見的兩鍵（`canonical` 路徑、`read_only`），不再是一張永遠可能少一項的清單。
- 力氣改投在判準判定為 in scope 的兩件事上：commit 前的內容等價對帳（寫入迴圈自己有 bug 就會發生，不需要任何人犯錯），以及讓「審核過」對應到人真的看過東西的分層抽樣 diff。
- **被否決的兩個選項**（理由見 `#175` 路線變更留言）：寫到副本再換名以消滅不可逆；`--confirm` 最後一步要求 interactive TTY。後者形狀與（2026-09-08 當時的）契約 #2 一致，隨時可補，本輪未做的理由是它會預先決定操作者的工作方式。
- 本判準適用於本專案所有守門設計（MCP 唯讀邊界、outbound 授權、import 前置條件），不限 `#175`。

## 2026-09-24 補記：MCP 寫入工具的適用（`#28`，Sean 拍板）

`#28`（`mail_attachment_export`，第一個寫 host 檔的 MCP 工具）重演了 `#175` 的軌跡：codex-review 連三輪在同兩處補洞，分別是寫檔失敗後的清理，以及契約 #1 的 AST guard；觸及輪數上限後，做了驗收走查與三方會談。這三輪的審查都沒有拿到本判準。套用後的劃線如下：

- **受益人／principal**：Sean。**confused deputy**：被信件內容誘導的 CoWork，它的能力只有選工具參數（`attachment_ids`、`dest_dir`），外加透過信件影響附件的 bytes 與檔名。
- **防**：只靠上述能力就能觸發的問題；良性並發下的資料損失（使用者、同步軟體、防毒同時在同一目錄動作）；違反 issue 明文結構的改動。`dest_dir` 指向開機自動執行位置屬於這一側，另開 `#205` 處理。
- **不防，接受為殘留風險**：需要一個與 Sean 同權限、存心破壞的本機行程才能觸發的狀況，例如暫存檔 handle 關閉後、rename 之前的目錄競態。那種行程本來就能直接刪改 Sean 的任何檔案。單一附件整檔讀入記憶體也接受，因為它的大小受郵件伺服器的單封上限約束。
- **AST guard 是回歸絆索**：它擋的是作者或 agent 順手從錯的模組 import，所以形狀是 allowlist 加反射禁令，而且每條規則都要有配對變異測試，證明拿掉就會漏。刻意寫出來的混淆屬於作者違背自己的意圖，由 issue 明文禁令與 anchor 檔的跨模型審查處理。

**對審查的要求**：守門類改動送 `/codex-review` 時，第 1 輪的 domain context 就要附上本判準，以及該票的 principal／deputy 劃線。`#175` 與 `#28` 都是審查沒拿到判準、才一路追洞到輪數上限。
