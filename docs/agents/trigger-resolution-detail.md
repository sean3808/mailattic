# Trigger→Resolution 完整紀錄

> `trigger-resolution.md`（每個 session 載入的精簡版）各列的完整經過：成因、補救步驟、實測細節。以 `PC-NNN` 對應。遇到精簡版某列的症狀、而一句話的做法不夠用時讀這裡。

| Trigger 症狀 | Scope / preconditions | Resolution | Negative signal |
|---|---|---|---|
| equivalence / parity / golden 測試在實作改成委派上游後仍全綠 | 原本獨立的 A 與 B 已變成 A 直接呼叫 B，或兩邊共用同一組序列化設定 | 先確認兩側仍是獨立來源；若不是，改測我方真正擁有的介面形狀假設，對照物須獨立依上游實際行為推導 → mailattic/PC-079 | 兩邊一起改、測試仍通過，代表通過率 100% 但鑑別力為 0 |
| 手動編輯 `claude_desktop_config.json` 後重開 app，改動整個消失（移除的 MCP server 復活、新增的不見） | Claude Desktop 這類「app 自己也會寫」的 config 檔；Windows 上關視窗 ≠ 結束 process | 托盤圖示右鍵 Quit → 用 `Get-Process \| Where Name -like '*claude*'` 確認無殘留 → 才編輯 JSON → 重開 → mailattic/PC-074 | 症狀是「改了沒生效」而非「改了又變回去」時不適用——那是別的原因；不由 app 自己寫的 config 檔也不適用 |
| 為新加的守門寫的回歸測試是綠的，但「拿掉守門」不會讓它變紅 | 守門/白名單/剖析器類邏輯；多條檢查共用同一種失敗表現（同 exit code、同錯誤型別）；或斷言的是「某個保守上界仍在預算內」這類單邊比較 | 先問「把守門刪掉這條會紅嗎」，答不出來就實際註解掉跑一次；輸入調整成只違反被測那一條；斷言錯誤訊息屬於哪一條而非只看 exit code。若要證明某個計數項必要，拿**配對比較**（同一輸入下有該項與無該項的實際觀測差值），不要用單邊的「仍在上界內」——拿掉正數項只會讓值更小、更容易通過 → mailattic/PC-096 | 純資料轉換／計算類測試不適用（沒有多條規則共用同一種失敗表現的問題） |
| `pwsh -File script.ps1` 傳參後綁錯目標（給了值卻報「-X is required」，或 `-Target a b` 只收到 `a`） | `.ps1` 以 `pwsh -File` 為入口（非 dot-source / module）、參數 > 2 個、param block 未指定 `Position` | 一般情況加 `[CmdletBinding(PositionalBinding=$false)]` 強制全具名；但**腳本要自己分類原始參數時反而有害**（任何 `[Parameter()]` 會使其變 advanced script 並自動獲得 common parameters，`-p` 這類前綴相撞的 token 會在腳本本體執行前就被 binder 擋掉）→ 該情境完全不宣告 param block、直接讀 `$args` → mailattic/PC-091 | 單一參數的腳本，或以 dot-source / `Import-Module` 使用的函式庫不適用（那走正常 PowerShell 綁定，無 `-File` 的字串重新綁定問題） |
| worktree 內跑測試噴一整批 `ModuleNotFoundError` collection error，看起來像環境壞了 | 在 `.claude/worktrees/<name>/` 內、且繞過 canonical launcher 直接下 `uv run pytest`；worktree 是 fresh checkout（無 `.venv`），PATH 上有全域 pytest | 本專案一律走 `scripts\invoke-pytest.ps1`（它自己處理 interpreter），worktree 先 `uv sync`。已繞過而中招時：`uv run python -m pytest` 可證明是 interpreter 選錯而非缺套件 → mailattic/PC-077 | 不要因此 `uv add` / `uv sync` 補套件——dep 本來就在，根因是 interpreter；若 `uv run python -m pytest` 仍缺套件，那才是真的 venv 壞。主 repo（非 worktree）是否同症未驗證 |
| 長跑命令（Full route / coverage 雙跑 / 大 build）掛 `run_in_background` 仍在中途死掉，進度停在 ~78%、狀態顯示 killed | Claude Code 的 Bash / PowerShell 工具，預估 >8 分鐘的命令。`timeout` 參數上限 600000ms，**背景執行不豁免這個上限** | 寫一支絕對路徑的 runner `.ps1`（放 session scratchpad）：`Set-Location` → 跑目標命令 → `"EXIT=$LASTEXITCODE" \| Out-File <marker>.exit`；用 `Start-Process pwsh -WindowStyle Hidden -ArgumentList '-NoProfile','-ExecutionPolicy','Bypass','-File','<runner.ps1>'` 脫離工具管轄。**不要把命令內嵌成 `-Command` 字串**（多層引號靜默壞掉：行程起得來、log 0 bytes、exit 檔永不出現）。完成判定只認 exit 標記檔，不看 log 內容也不看行程是否消失；標記檔要抓**被測操作**的 exit code，不是包裝腳本或直譯器的 → mailattic/PC-118 | <8 分鐘的命令用普通 `run_in_background` 就好（有原生完成通知）；`codex exec` 這類已有 engine 看門狗契約的長跑走 engine 的 watchdog，不要兩套並用 |
| MCP 工具的邊界輸入拿到的錯誤訊息不是自己寫的那句，像驗證邏輯整段沒跑 | 工具參數宣告成 union（`int \| str`）或任何非純 `str` 型別；輸入是字串 | 框架會先對該字串跑 `json.loads` 才交給你的函式，且只 catch `JSONDecodeError` —— 非該型別的解析失敗（例：CPython 4300 位整數字串上限拋裸 `ValueError`）會穿過去變成框架錯誤，函式體根本沒執行。驗「我方訊息」的測試先確認輸入到得了函式體；到不了的改測判定 helper 本身，別對工具呼叫斷言。**不要因為「框架反正會擋」就拿掉自己規則裡的對應 clause** → mailattic/PC-104 | 宣告為純 `str` 的參數不適用（框架不 pre-parse）；in-process 直接呼叫函式的測試路徑也不適用（完全不經過 `pre_parse_json`） |
| commit 後 `--stat` 出現不屬於這次改動的檔案，或自己已 stage 的成果出現在別人的 commit 裡 | 同一 repo 此刻有第二個 agent／session 在寫；用了 `git add -A <dir>` / `git add .`；或走「先 stage → 跑數分鐘語意 gate → 才 commit」的流程（gate 要求先 stage，與「改完立刻 commit」直接衝突） | 共用 repo **一律列明確檔案路徑**，`git commit` 前用 `git diff --cached --name-only` 逐檔確認都是自己的。長 gate 流程改走 feature branch，或改成對「已 commit 的 diff」跑（不過再 amend）。**加害方完全無症狀**——commit 成功、測試照過，只有事後看 `--stat` 才發現。補救：`git reset --soft HEAD~1` → `git restore --staged <別人的檔>` → 用原訊息重新 commit → mailattic/PC-088 | 單人單 session 的 repo 不需為此改流程（曝險窗口存在但沒有第二個 writer 就不觸發） |
| push 推到非預期的分支，或要刪的分支 `git rev-parse` 回 `unknown revision` | 同一 repo 此刻有第二個 agent／session；規劃與動作之間隔了數次工具呼叫 | 落點以 `git commit` 輸出的 `[<branch> <sha>]` 為準，不沿用先前查到的分支名；push 前重查 `git branch --show-current` 與 `git rev-list --left-right --count origin/<branch>...HEAD`；刪分支把「列 SHA → 驗祖先關係 → 刪」寫成同一次工具呼叫，讓查證與動作之間沒有空隙（順帶把 SHA 印出來當 reflog 復原錨點）→ mailattic/PC-133 | 單人單 session 不觸發。實測切換頻率高於「一輪操作」的粒度——「上一輪 `git branch` 的輸出」在共用 repo 的保鮮期以分鐘計，不是現況 |
| `/closeout` 的 gate 紅了，失敗訊息裡出現 `VIRTUAL_ENV does not match the project environment path` 或「Resolved project Python does not exist」，但同一測試用 canonical launcher 跑是綠的 | closeout runner 以 `uv run --script closeout_gates.py` 啟動（uv 把 script cache env 的 `VIRTUAL_ENV` 傳給子行程）；且失敗的測試自己會再呼叫 `uv`（本例 `install-release-pre-push.ps1` 用 `uv python find`），警告字串被串進路徑 | 用 `scripts\invoke-pytest.ps1` 對同一測試取證，綠即可判為 runner 環境 artifact 而非真缺陷；要看成因讀該次 run 目錄的 `gate-output.log`，`VIRTUAL_ENV=...closeout-gates-*` 直接印在斷言訊息裡。**實際是兩個測試**（`test_installer_composes_pre_commit_wrapper_and_raw_stdin_companion` 與 `test_installer_preserves_explicit_default_core_hooks_path`），`smoke-test` 因 `-x` 只顯示第一個，要 `full-test-suite` 才看得到兩個。根治在 closeout skill 側：runner 對 gate 子行程清掉 `VIRTUAL_ENV` → mailattic/PC-168 | 失敗測試本身不呼叫 `uv` 就不是這條。**「在乾淨 shell 跑一次子集合全綠」不足以判定** —— 洩漏來自 runner 自己的行程環境，重現必須經由 runner |
| `git merge-base --is-ancestor <branch> origin/main` 對**每一支**分支都回非零（含五分鐘前才併進 main 的那支）；或 `git diff main <branch>` 顯示舊分支差一百多個檔 | squash-only 的 repo（本 repo `allow_merge_commit` / `allow_rebase_merge` 皆 false）；要判斷「這個分支併了沒」 | squash 產生的是內容相同但 SHA 全新的 commit，原 tip 永遠不會成為 main 的祖先；雙點 diff 又含「main 從分支點後新增的一切」。可用判準依成本排序：(1) upstream 是否 `[gone]`（`git for-each-ref --format='%(upstream:track)' refs/heads/<b>`）；(2) 內容比對兩步——先 `git diff main...<b> --name-only`（三點）取分支自己改過的檔，再 `git diff main <b> -- <那些檔>` 看是否為空。`git cherry` 同樣不可靠（多 commit 被壓成一個，patch-id 全對不上）→ mailattic/PC-167 | 允許 merge commit 的 repo 不適用，那裡祖先關係本來就是對的判準。第 2 點只證明「內容一不一樣」，**不證明**差異是有價值的未併工作還是舊版本殘留 —— 不可拿它當「可以刪」的充分條件 |
| 守門類改動（授權門、邊界 guard、不覆寫／不刪除保證）的跨模型語意審查每輪都答得出「還能怎麼繞過」，補一個洞換下一個，一路撞上輪數上限 | 送 `/codex-review`（或 `/closeout` 的 semantic-review 格）的改動屬守門類；審查沒拿到威脅模型 | 第 1 輪 domain context 就附上守門判準 [D-20260908-1](../decisions/D-20260908-1-guards-defend-confused-deputy-not-deliberate-collision.md) 與該票的 principal／confused deputy 劃線（deputy 有哪些能力），列出明文接受的殘留風險，以及 issue 已拍板、不在審查範圍的設計（例：對話層授權、否決的工具層核可），要求審查不要重提。AST／import guard 的形狀直接選 allowlist 加反射禁令 → mailattic/PC-204 | 純功能／資料轉換的改動沒有「繞過」這個問題軸；判準寫進 context 後審查仍在判準內側找到問題 → 那是真缺陷，照修 |
